# Разбор документов в JSON

Тестовое задание А (LLM Engineer). CLI получает текст документа (счёт, КП, акт) и возвращает JSON по
фиксированной схеме. Главная цель — не выдумывать то, чего в документе нет.

Стек: Python 3.11+, pydantic (схема и валидация), OpenAI SDK (Structured Outputs), pytest.

## Запуск с нуля

Нужны Python 3.11 или новее и `make`.

```bash
make install
```

```bash
make eval
```

```bash
make test
```

`make install` создаёт `.venv` и ставит зависимости. `make eval` прогоняет все 12 документов и
печатает отчёт. Ключ API и сеть для этого не нужны (почему — в разделе «Вызов LLM»).

Разобрать один документ:

```bash
.venv/bin/python -m extractor data/docs/03_invoice_kokzhiek_ocr_bin.txt
```

В stdout печатается только JSON по схеме, диагностика идёт в stderr. Код выхода `0` — результат
принят, `2` — автоматический разбор не удался и результат пустой.

Без `make`: `python3 -m venv .venv && .venv/bin/pip install -r requirements.txt`, затем
`.venv/bin/python eval.py` и `.venv/bin/python -m pytest`.

### Переменные окружения

| Переменная | Нужна | Назначение |
|---|---|---|
| `OPENAI_API_KEY` | только для режима `openai` | ключ OpenAI |
| `OPENAI_MODEL` | нет | модель, по умолчанию `gpt-6-luna` |

Их можно записать в файл `.env` (образец — `.env.example`): `make` подхватит его сам.

С ключом:

```bash
make eval LLM=openai
```

```bash
make record
```

`make record` заново прогоняет набор на настоящей модели и перезаписывает её ответы в
`data/responses`.

## Вызов LLM

Используется модель `gpt-6-luna` через OpenAI Responses API со Structured Outputs
(`OpenAIClient` в `extractor/llm.py`).

Чтобы проверяющему не нужен был ключ, ответы модели записаны в `data/responses`: по одному файлу на
документ, в поле `source` указано `openai:gpt-6-luna`. `make eval` по умолчанию работает в режиме
`replay`: читает эти файлы и прогоняет их через тот же конвейер — валидацию, проверки по тексту и
сравнение с эталонами. Имя файла — хэш текста документа, поэтому для изменённого или нового
документа записанного ответа нет и нужен режим `openai`.

Запись сделана одним прогоном 20.11.2026. Ответы модели не детерминированы, повторный `make record`
может дать другой результат.

До прогона на настоящей модели конвейер отлаживался на ответах, написанных вручную, с заложенными
ошибками: исправленный после OCR БИН, вычисленные НДС и итог, выполненное указание из текста
документа, ответ не по схеме. Эти файлы остались в истории (коммит `89a59c2`), а те же случаи
покрыты тестами в `tests/`.

## Как устроен конвейер

1. **Вызов модели** (`extractor/llm.py`). Модели передаются инструкция (`extractor/prompt.py`), текст
   документа в тегах `<document>` и JSON-схема в режиме `strict`.
2. **Валидация** (`extractor/schema.py`). Ответ разбирается pydantic-моделью `Extraction`: БИН — ровно
   12 цифр, дата — настоящая календарная дата, валюта и тип — из списка, суммы неотрицательны,
   лишние и пропущенные поля запрещены.
3. **Проверки по тексту** (`extractor/checks.py`). Обычный код без LLM сверяет значения с документом.
   Схема гарантирует форму ответа, но не то, что значение взято из документа.
4. **Результат** — всегда валидный объект схемы.

### Если ответ не прошёл валидацию

- Модель получает второй запрос с текстом ошибки валидации. Попыток всего две.
- Если и вторая попытка невалидна или модель недоступна, наружу уходит пустой результат:
  `doc_type: "unknown"`, все поля `null`, уверенность `0`, в `warnings` — причина и пометка «нужен
  ручной разбор». CLI завершается с кодом `2`. Невалидный ответ дальше не передаётся.
- На записанном прогоне повтор не понадобился ни разу: в режиме `strict` модель не может нарушить
  структуру ответа. Повтор и закрытый отказ проверяются тестами в `tests/test_pipeline.py`.

### Что проверяет код после модели

| Поле | Условие | Если не выполнено |
|---|---|---|
| `supplier_bin` | эти 12 цифр подряд есть в тексте | `null` + предупреждение |
| `doc_number` | номер есть в тексте (без учёта пробелов и регистра) | `null` + предупреждение |
| `doc_date` | число и год этой даты есть в тексте | `null` + предупреждение |
| `supplier_name` | хотя бы одно слово названия есть в тексте | `null` + предупреждение |
| `currency` | валюта названа в тексте (тенге, тг, ₸, USD, $, EUR, € …) | `null` + предупреждение |
| `vat_amount` | такая сумма написана в тексте | `null` + предупреждение |
| `total_amount` | такая сумма написана в тексте цифрами | значение остаётся, предупреждение, уверенность ≤ 0.3 |
| `total_amount` | сходится с суммой позиций (с НДС или без) | предупреждение, уверенность ≤ 0.3 |

Итог не обнуляется, потому что сумма может быть написана только прописью, а переводить слова в
число умеет только модель. НДС обнуляется: посчитанный моделью НДС — прямое нарушение условия.

## Правила для противоречий

Противоречие всегда попадает в `warnings`, а поле заполняется так:

- **Две разные даты документа** — берётся дата из заголовка рядом с номером («№ 318 от 14.10.2026»).
  Срок действия, срок оплаты и дата поставки датой документа не считаются и противоречием не являются.
- **Две разные итоговые суммы** — берётся та, что равна сумме позиций. Если проверить нельзя —
  первая по тексту.
- **Сумма цифрами и прописью расходятся** — берётся сумма цифрами.
- «Итого» без НДС и «Всего к оплате» с НДС — не противоречие: `total_amount` — это сумма к оплате.

Правила записаны в инструкции для модели. Кодом проверяется только расхождение итога с суммой
позиций, остальное зависит от модели.

## Решения по неоднозначным местам задания

1. **БИН, повреждённый OCR** (`2l064090Ol80`). Считаю, что такого БИН в документе «нет»: `null` и
   предупреждение. Восстановленный по похожим символам БИН выглядел бы уверенно, но это догадка, а
   ошибка в БИН стоит дорого. То же правило — для даты и суммы с буквами вместо цифр.
2. **«НДС не облагается»**, «Без НДС», только ставка в процентах — `vat_amount: null`, а не `0`.
   Сумма НДС в документе не написана. `0` ставится, только если написано «НДС: 0».
3. **Итог в КП без строки «Итого»** — `null`. Складывать позиции нельзя: это вычисление, а не
   извлечение.
4. **`field_confidence`** в задании показан с одним ключом. Сделал уверенность для всех восьми
   скалярных полей. Это самооценка модели, код может её только понизить. Она не откалибрована.
5. **`supplier_name`** — как написано в документе, с формой собственности; из двух языковых вариантов
   берётся первый по тексту.
6. **Тип документа** определяется по названию, а не по номеру: «Шот-фактура № AKT-09» — это `invoice`.
7. **`price`** в позиции — цена за единицу, а не сумма строки.

## Отчёт eval

Вывод `make eval` на записанных ответах `gpt-6-luna`:

```

Прошли валидацию со второй попытки: 0
Не прошли валидацию (результат пустой): 0

Поле                 Точность  Галлюцинации  Пропуски  Неверные
doc_type         12/12 (100%)             0         0         0
supplier_name    12/12 (100%)             0         0         0
supplier_bin     12/12 (100%)             0         0         0
doc_number       12/12 (100%)             0         0         0
doc_date         12/12 (100%)             0         0         0
currency         12/12 (100%)             0         0         0
total_amount     12/12 (100%)             0         0         0
vat_amount       12/12 (100%)             0         0         0
line_items       12/12 (100%)             0         0         0
ВСЕГО          108/108 (100%)             0         0         0

Предупреждения: нужны в 5 документах, выданы в 5; лишние — в 0 из 7 документов без проблем.
```

Как читать:

- **Галлюцинация** — поле заполнено, хотя в эталоне `null`. **Пропуск** — `null`, хотя в эталоне есть
  значение. **Неверное** — заполнено и там и там, но по-разному. Считаются раздельно.
- Правильный `null` засчитывается как верный ответ.

Что этот результат значит и чего не значит:

- 100% на 12 документах — это один прогон на маленьком наборе, а не оценка качества. Эталоны и
  инструкцию писал один человек по одним и тем же правилам, поэтому набор проверяет, следует ли
  модель инструкции, но не находит случаи, о которых я не подумал.
- Все значения модель вернула верно сама: проверки по тексту не изменили ни одного поля. Код добавил
  два предупреждения: в `07` (итог написан только прописью) и в `09` (итог не сходится с суммой позиций:
  сумма НДС повреждена, и код не может её учесть). То есть на этом прогоне проверки отработали как страховка, а не
  как исправление.
- В `03` и `09` модель не стала восстанавливать повреждённые БИН, дату и НДС, в `10` не выполнила
  указание из текста документа, в `06` выбрала итог, равный сумме позиций.
- `field_confidence` оказалась неинформативной: модель ставит от 0.9 до 1.0 всем полям, включая те,
  что вернула как `null`. Использовать её для отбора документов на ручную проверку нельзя.

## Что сделано и что нет

Сделано: CLI, схема с программной валидацией, повтор и закрытый отказ, проверки по тексту, 12
документов с эталонами, eval одной командой, 23 автотеста.

Не сделано:

- Прогон на настоящей модели один, на 12 документах. Разброс между прогонами не измерялся.
- Расход токенов и стоимость одного документа не измерялись.
- Проверка «значение есть в тексте» не отличает БИН поставщика от БИН покупателя или от цифр,
  подставленных в текст злоумышленником.
- Позиции (`line_items`) по тексту не сверяются.
- Месяц в дате не проверяется кодом: он бывает записан словом на двух языках.
- Сумма НДС, написанная только прописью, будет обнулена.
- Вход — только текст. PDF, сканы и сам OCR не реализованы.
- Нет HTTP-сервиса, только CLI.
